# Plan: Embed and Install the Bridgectl Operations Skill

## Goal

Ship the `bridgectl-ops` Agent Skill inside the `bridgectl` binary and add a
local-only `bridgectl skill install` command that materializes the embedded
skill for agents. The command will support the generic Agent Skills layout,
with safe global, project-scoped, and explicit-directory destinations.

## Current State

- The CLI entry point is `tools/bridgectl/main.go`, which delegates command
  registration to the `internal/cli` package (`tools/bridgectl/main.go:1-10`).
- Root command initialization currently loads bridgectl configuration for every
  command (`internal/cli/root.go:37-74`), while command groups register through
  `init` functions such as `internal/cli/plugin.go:347-350`.
- Production web assets establish the repository's compile-time embedding
  precedent: the Go package that owns the asset tree declares `//go:embed` and
  exposes an `embed.FS` (`internal/web/assets.go:1-25`). Go embed patterns cannot
  reach the repository's sibling `skills/` directory from `internal/cli`, so
  the skill asset package must be co-located with `skills/bridgectl-ops`.
- The canonical skill tree already contains `SKILL.md`, references, and safe
  templates under `skills/bridgectl-ops/`; local evaluation artifacts are
  intentionally ignored and are not distributable.
- The skill's ecosystem reference already points agents to the published
  documentation and its `llms.txt` index (`skills/bridgectl-ops/references/ecosystem.md:15-21`).
  The wording will explicitly identify `llms.txt` as the complete published
  documentation reference without duplicating the URL.
- CLI Markdown pages are generated by `bridgectl doc` (`internal/cli/doc.go:9-35`)
  and the checked-in root page currently lists all registered commands but no
  `skill` command (`docs/cli/bridgectl.md:17-35`).
- The repository requires behavior changes to update local docs and
  `CHANGELOG.md`, and CLI/API changes must be synchronized with the separate
  public documentation checkout (`AGENTS.md:27-49`).

## Decisions

- **Use the generic Agent Skills layout.** A global install resolves to
  `~/.agents/skills/bridgectl-ops`; `--project` resolves to
  `./.agents/skills/bridgectl-ops` relative to the current working directory.
  This follows the user's selected scope and avoids coupling the CLI to one
  agent vendor.
- **Make `--dir` an exact destination directory.** `--dir /path/to/skill`
  installs directly into that directory, rather than appending another skill
  name. `--dir` and `--project` are mutually exclusive, and an omitted `--dir`
  uses the global or project default.
- **Require `--force` to replace an existing destination.** A normal install
  must not overwrite a user's existing skill directory. `--force` replaces the
  managed skill tree only after all embedded files have been staged; a
  destination symlink is rejected rather than followed.
- **Embed only distributable skill files.** Embed `SKILL.md`, `references/`,
  and `assets/` from the canonical skill directory. Do not embed ignored local
  evaluation files or the Go embedding source file.
- **Keep installation independent from ERPBridge configuration.** The command
  performs no server, context, or credential operation; it only writes the
  embedded files and reports the redacted destination.
- **Use the published `llms.txt` index as the complete documentation entry
  point.** The skill will tell agents to consult
  `https://blog.nimendra.xyz/erpbridge-docs/llms.txt` before focused published
  pages, while preserving the local source and generated CLI docs as the
  checkout's source of truth.
- **Follow the supplied Graphify installer pattern selectively.** Adopt its
  explicit project-scope switch and materialization of packaged skill files,
  but keep ERPBridge's smaller generic-layout interface instead of adding
  vendor-specific platform installers.

## Scope

In scope:

- A co-located Go `embed.FS` package for the distributable
  `bridgectl-ops` skill files.
- `bridgectl skill install` with `--project`, `--dir`, and `--force`.
- Safe staged installation, path resolution, collision handling, and focused
  CLI tests.
- Skill documentation wording, generated CLI reference pages, local README /
  docs navigation, changelog entries, and the corresponding public docs page.
- Build/test verification that the normal CLI build includes the embedded
  assets.

Out of scope:

- Installation adapters for Claude, Pi, Codex, Cursor, or other vendor-specific
  skill directories.
- Downloading skill files or published docs at runtime.
- Embedding ignored `skills/bridgectl-ops/evals/` artifacts.
- Changes to ERPBridge server APIs, credentials, contexts, or runtime plugin
  behavior.

## Verification

- `bridgectl skill install` writes the exact embedded `SKILL.md`, reference,
  and template files to `~/.agents/skills/bridgectl-ops` by default.
- `bridgectl skill install --project` writes only under
  `./.agents/skills/bridgectl-ops`.
- `bridgectl skill install --dir <destination>` writes directly to the
  requested directory; `--dir` plus `--project` fails before any write.
- Existing destinations fail without `--force`; `--force` replaces the staged
  managed tree, and destination symlinks are never followed.
- The installed skill includes the complete published docs index URL and does
  not include credentials, raw environment configuration, or ignored evals.
- The command appears in generated CLI docs, local and public documentation
  builds pass, and the CLI binary builds without runtime asset downloads.
